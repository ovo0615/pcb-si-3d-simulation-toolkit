# 眼圖量測介面調查（AEDT 2026.1）

此工具由虎門科技資深技術工程師 Jeff Hong 洪敬傑提供

第 5 階段的前置工作（5A）。目的是回答一個問題：**AEDT 2026.1 到底能不能給出
可比對的眼圖數值**，答案決定 Golden Baseline 的驗收標準怎麼訂。

結論先講：**標準 QuickEye 與 IBIS-AMI 都可以取得完整眼圖量測**，AMI 原本取不到
是因為求解的 Setup 選錯，不是 AEDT 不支援。ADR-0039 預留的「AMI 退回只比
impulse」條款用不到了。

## 1. gRPC 無法區分「方法不存在」與「參數錯誤」

這是最該先知道的一件事，因為它決定能力偵測不能靠例外型別。

以不存在的方法名與真實方法名各呼叫一次，錯誤完全相同：

```
ThisMethodDoesNotExistAtAll  GrpcApiError: Failed to execute gRPC AEDT command: ThisMethodDoesNotExistAtAll
AddAllEyeMeasurements        GrpcApiError: Failed to execute gRPC AEDT command: AddAllEyeMeasurements
AddTraceCharacteristics      GrpcApiError: Failed to execute gRPC AEDT command: AddTraceCharacteristics
```

`getattr` 也沒有鑑別力——`AedtPropServer` 是動態派發，任何名稱都取得到方法物件。

**因此能力偵測只能看結果**：呼叫後實際匯出表格並檢查有沒有數值欄。這正是現行
`circuit_export._extract_eye_measurements` 用 `except: continue` 會靜默降級的原因，
也是 ADR-0039 要求「明確不可得加原因」的依據。

## 2. 標準 QuickEye：`AddAllEyeMeasurements` 優於現行做法

測試件：`lowpass.s2p`＋EYESOURCE／EYEPROBE，4 Gbps，Tr/Tf = 0.2 UI，
`NexximQuickEye`，求解 5.7 秒。

| 做法 | 取得項目 | 表格方向 |
|---|---|---|
| 現行 `AddTraceCharacteristics`（逐項） | 2 項 | 欄導向（首列名稱、次列數值） |
| `AddAllEyeMeasurements`（一次全部） | **11 項** | **列導向（每列一項）** |

兩者的 EyeHeight 與 EyeWidth **完全一致**（0.2217 V／0.9171 UI），可確認不是不同
定義的量測。`AddAllEyeMeasurements` 另外給出 EyeLevelZero／One、EyeAmplitude、
EyeSignalToNoise、EyeOpeningFactor、EyeJitterP2P、EyeJitterRMS、MinEyeWidth、
MinEyeHeight。

**表格方向會反過來**，改用新 API 時解析器必須跟著改，不能沿用現有的欄導向解析。

現行程式註解寫「抖動與開口面積在 QuickEye 常回 NaN」——本次實測 EyeJitterP2P
0.0359、EyeJitterRMS 0.0138 都有值，該註解對 2026.1 已不成立。

## 3. AMI：量測取不到是求解 Setup 選錯，不是不支援

測試件：`AMI_Example` 的 `diff_line.s4p`＋`ibis_ami_example_tx/rx`，4-Port 差動，
4 Gbps，32 samples/UI。

| 已求解的 Setup | contour 眼圖匯出結果 |
|---|---|
| 只解 `VerifEyeAnalysis`（NexximVerifEye） | **只有 11 個量測名稱，沒有數值、沒有探棒欄** |
| 解 `AMIAnalysis`（NexximAMI） | **11 項全部有數值** |

AMI 報表的資料源固定是 `AMIAnalysis` solution。只解 VerifEye 時該 solution 沒有
資料，AEDT 仍會接受 `AddAllEyeMeasurements` 並列出名稱，但匯不出任何數值——
**一個「呼叫成功卻沒有結果」的典型案例**。

解了 `AMIAnalysis` 之後取得：

```
EyeLevelZero      -126.4571        EyeWidth           0.8125
EyeLevelOne        124.4929        EyeJitterP2P       0.1936
EyeAmplitude       250.9500        EyeJitterRMS       0.0312
EyeHeight          105.0925        MinEyeWidth        0.8164
EyeSignalToNoise     5.1615 (SI)   MinEyeHeight     138.4630
EyeOpeningFactor     0.8063 (SI)
```

**這對現行程式是一個實質問題**：`ami_channel.py` 在 Statistical 模式只解
`VerifEyeAnalysis`（`solve_setup = circuit.create_setup("VerifEyeAnalysis", ...)`），
報表卻建在 `AMIAnalysis` 上。依本次結果，該路徑即使加上量測也會是空的。

矩形眼圖（`AMIEyeDiagram`，帶 `auto_compute_eye_meas`）在兩種情況下都取不到
數值，**contour 眼圖才是帶量測的那一個**。

## 4. 訂容差前必須先處理的三件事

- **單位不一致**：標準 QuickEye 的 EyeHeight 是 0.2217（V），AMI 是 105.0925
  （mV）。跨案例比對前必須正規化，否則差三個數量級。
- **`(SI)` 後綴**：EyeSignalToNoise 與 EyeOpeningFactor 的值帶 ` (SI)`，解析時要
  處理，不能直接 `float()`。
- **Min 系列的定義未知**：兩個案例都出現 `MinEyeHeight > EyeHeight`、
  `MinEyeWidth > EyeWidth`。在查清定義之前不得用於規格判定。

## 5. 環境與適用範圍

- AEDT：2026.1（`odesktop.GetVersion()` 回報 2026.1.0），非圖形化 gRPC。
- 調查階段使用 MCP 端的 PyAEDT 1.3.0；**已於出貨用的後端 venv（PyAEDT 1.2.0）
  以 `probe_eye_measurements.py` 重跑確認，三個案例的結論與數值完全一致**
  （QuickEye 眼高 0.2217、AMI 眼高 105.0925、只解 VerifEye 時如實回報不可得）。
  原始結果見 `eye_measurement_probe.json`。
- 測試件為 Ansys 安裝目錄內的唯讀範例，依 ADR-0042 未複製進版控。
- 兩個 Statistical 案例的求解時間：QuickEye 5.7 秒、AMI VerifEye 19.4 秒、
  AMI AMIAnalysis 25.4 秒。

現象：兩條 Lane 的 Circuit 都建立成功、Setup 也建立成功，日誌停在

日誌，表示求解引擎根本沒有啟動。Windows 事件記錄沒有對應的當機紀錄。

已排除的三個假設，各以獨立探測驗證（都正常完成）：

也就是說，用同一組模型、同樣的兩條 Lane、同樣的設定與交叉綁定、同樣從暫存副本

### 二分定位結果

把出貨路徑拆成「建構」與「求解呼叫」兩段各測一次：

| 階段 | 內容 | 結果 |
|---|---|---|
| build | 出貨路徑的 `_build_circuit`（涵蓋 `_new_circuit`、`ascii_safe_touchstone`、`_create_touchstone_component`、`_component_pin_map`）＋ 自己的 `analyze_setup` | **通過，30.5 秒** |

```python
circuit._desktop.ClearMessages(circuit.project_name, circuit.design_name, 0, 3)
```

它包在 `try/except` 裡，但**卡住不是例外**，攔不到。

### 但證據隨後變得不確定

為了精確計時而把 `ClearMessages` 拆出來單獨呼叫後重跑同一階段，這次卻在
**建構階段**就丟出 `TypeError: unsupported operand type(s) for /: 'NoneType'

因此目前只能說：`ClearMessages` 是**唯一剩下的候選且確實卡過一次**，但同一條
路徑會出現兩種不同的失敗模式，代表這不是單一行程式的確定性缺陷。今天反覆啟動
與強制結束了十幾個 AEDT 工作階段，環境狀態可能是干擾因素；重新驗證前建議先讓
機器回到乾淨狀態。

### 根因：授權席次被佔滿（2026-08-14 確認）

授權日誌給出決定性證據。成功的求解一定會看到 Circuit 求解引擎簽出授權：

```
18:49:00 CHECKOUT elec_solve_level1/2/3  NEXXIM.EXE  →  18:49:22 CHECKIN（22 秒）
19:19:19 CHECKOUT elec_solve_level1/2/3  NEXXIM.EXE  →  19:19:43 CHECKIN（24 秒）
19:26:36 CHECKOUT elec_solve_level1/2/3  NEXXIM.EXE  →  19:27:02 CHECKIN（26 秒）
```

**最後一次成功是 19:27:02。之後所有卡住的執行，`NEXXIM.EXE` 完全沒有出現**——
求解引擎根本沒被啟動，這也解釋了求解目錄裡為何沒有任何求解器日誌。卡住的
AEDT 只簽出了 `electronicsckt_gui` 與 `electronics_desktop`，然後每分鐘 heartbeat，
其中一次在四分鐘後記錄：

```
ERROR  License Handler Disconnected: System error: 10054（遠端主機強制關閉連線）
```

統計當日未歸還的授權：`electronics_desktop` 14 個、`electronics2d_gui` 7 個、
`electronicsckt_gui` 6 個、`elec_solve_level1` 4 個。而簽出紀錄的席次欄顯示
`electronicsckt_gui` 只有 2 個席次——**席次已被佔滿**，因此求解授權要不到。

這些未歸還的簽出來自被強制結束、沒有正常釋放的 AEDT 工作階段。驗證期間反覆
啟動與中止工作階段是主要來源。

授權伺服器設定本身也有問題，會放大這個情況：

| 伺服器指定方式 | 1055（Licensing Interconnect） | 2325（FlexNet） |
|---|---|---|
| 以主機名指定 | 通 | **不通** |
| 以 IP 指定 | **不通** | **不通** |

（實際的主機名與 IP 刻意不寫出來：那是內網設定，對結論沒有貢獻，
而寫進版本庫就會跟著文件到處走。）

**結論：卡住不是工具的缺陷。** 先前懷疑的 `ClearMessages` 只是剛好在等待點之前，
與根因無關。重新驗證前必須確認授權席次已釋放（等伺服器逾時回收，或請授權管理者
清除殘留簽出）。

### 不論根因為何都該做的事

`_analyze_or_raise` 沒有任何逾時保護。上面兩次卡住分別靜默了 9 分鐘與 25 分鐘，
都是從外部檢查程序才發現的。這是把「AEDT 偶發問題」放大成「整個執行無限期停住」
的原因，應優先補上，與根因無關。

（後續已確認根因是授權席次，`ClearMessages` 並非肇因；以下仍值得做，因為它會
讓授權問題以明確的錯誤呈現，而不是無聲卡住。）

`ClearMessages` 本身的用途只是在求解前清掉舊訊息，讓 `_aedt_error_messages` 只
看到本次的訊息。它可以用「記下求解前的訊息數、之後只取新增部分」取代，既保留
原意又不會阻塞。

**另一個已確定要修的問題**：`analyze_setup` 是阻塞呼叫，AEDT 卡住時不會逾時。
上次那個執行掛了九分多鐘毫無反應，是從外部檢查才發現的。分段求解已有 stall
偵測，IBIS／AMI 這條路徑沒有對應保護，應補上。


## 結案：根因與端對端結果（2026-08-14）

### 根因是 ClearMessages，不是授權

先前把矛頭指向授權席次是錯的。用單一變數對照確認：同一組電路、同樣兩條 Lane、
同樣設定、同樣兩個 Setup 都解，唯一差別是求解前有沒有呼叫 `ClearMessages`。

| 變體 | 差異 | 結果 |
|---|---|---|
| A | 直接 `analyze_setup` | 通過（27.2 秒 ＋ 7.2 秒） |
| C | 求解前先 `ClearMessages` | 卡住（420 秒逾時，AEDT 隨後消失） |

`ClearMessages` 會正常回傳，之後 `analyze_setup` 才卡死，因此 `try/except` 攔不到。

**為什麼會查錯方向**：先前單獨測過 `ClearMessages` 並判定無害，但那次呼叫之後只做了
輕量的 `GetVersion`，沒有接著求解——驗證設計不完整。加上 2D 萃取引擎正好在同一段
時間佔用求解授權，讓授權線索看起來很有說服力。二分法其實一開始就指對了。

修法：不清空訊息佇列，改為記下求解前的訊息數，之後只取新增部分（`_aedt_message_count`）。
語意相同，但不動 AEDT 的訊息佇列。標準 IBIS 與 AMI 兩條路徑都已改。

### 另一個實作疏漏：Lane 2 拿不到量測

「只保存第一顆 Probe」的限制在**每個 Lane 自己的專案內仍然生效**。兩條 Lane 的
元件都建立（保留串擾，這是對的），但目標 Lane 的 Probe 若不是第一顆就取不到數值。
修法：把目標 Lane 的元件放到最前面，兩條 Lane 仍完整建立，只改放置順序。

順帶修掉一個副作用：Seed 原本綁放置順序，重排後同一條 Lane 在兩次執行會拿到不同
碼型，串擾激勵不一致。已改為綁定 `lane_id`。

### 端對端結果

`probe_ami_dual_single.py`，`diff_line.s4p` 兩條單端 Lane，NRZ、32 samples/UI：

| 速率 | Lane 1 眼高／眼寬 | Lane 2 眼高／眼寬 |
|---|---|---|
| 1 Gbps | **39.1646 mV／0.6769 UI** | **37.3368 mV／0.6615 UI** |
| 4 Gbps | 眼圖閉合 | 眼圖閉合 |

兩條 Lane 的數值不同（39.16 vs 37.34），這是耦合 S4P 上非對稱串擾的預期表現，
反向佐證串擾確實保留、S4P 沒有被拆成兩個 S2P。4 Gbps 閉眼是物理結果而非量測失敗，
工具如實標示「眼圖閉合，無法量測」而不是回報 0。

## AMI 參數路徑：四個只有真實模型才會踩到的缺陷（2026-08-14）

以真實廠商模型（USB4 Tx／Rx）實跑時，一天內連續遇到四個缺陷，每一個都會讓分析
在建立 Circuit 階段就中止。**四個全部被 Ansys 內建範例避開**——範例的 AMI 參數
太單純，觸發不到這條路徑。

### 1. Range 取前兩個值

`(Range 7 0 15)` 是 `(typ, min, max)`，取前兩個會得到 min=7、max=0。規格內的預設值
7 因此被自己的驗證判成「大於最大值 0」。

**辨識線索：介面上的範圍標籤顯示成「7～0」。** 反向的範圍就是 min／max 讀反了。

### 2. 保留參數被寫入

USB4 把 `DLL_Path`／`DLL_ID` 宣告成 `(Usage In)(Value "placeholder")`。保留區的
`Usage In` 在 AMI 規格裡代表「由 EDA 工具傳給模型」，AEDT 會自己填實際路徑。
工具若當成可編輯欄位並寫入 `"placeholder"`，回讀得到 AEDT 的 `"."` 而判定失敗。

判定可編輯要**同時**檢查 `Usage` 與所在區段（只有 `Model_Specific` 可編輯）。

### 3. 解析結果快取在 Manifest

參數表在匯入時就解析並存進 `model_manifest.json`，之後不再重新解析。**改對解析
程式不會修好已匯入的模型**，使用者重啟後仍看到舊資料。必須連帶提高
`LIBRARY_SCHEMA_VERSION` 觸發重新解析，並確認遷移有寫回磁碟。

這個坑同一天踩到兩次（Range 與保留參數各一次）。

### 4. AEDT 回報設定失敗但值已寫入

`GEN=3` 設定後回讀也是 `3`，但 `_change_property` 回傳假值，判斷式
`if not changed or not equivalent(...)` 因此中止分析。

回讀是唯一能證明狀態的證據，回傳值只是輔助。改為只看回讀，回傳值為假時記錄日誌
而不中止；回讀不符仍照舊失敗。

### 對 Golden Baseline 的意涵

Golden Baseline 驗證的是**求解與量測的數值正確性**，不是**模型解析的健壯性**——
兩者需要不同的輸入。原廠範例可公開、適合前者；後者只能靠真實模型，而真實模型
不進版控。因此每次動到參數解析或寫入時，至少要用一個真實模型手動跑完整流程。
已寫入 `golden/README.md`。
