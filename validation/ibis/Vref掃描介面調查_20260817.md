# Vref 掃描介面調查（AEDT 2026.1）

此工具由虎門科技資深技術工程師 Jeff Hong 洪敬傑提供

## 一句話結論

**判準位（交越振幅）是眼圖報表的後處理屬性，改它不必重解——實測每點 0.14 秒。**
掃 13 點花 1.8 秒，整份求解結果重用。

寫入的正確方式是子物件的 `SetPropValue`，屬性叫 `Crossing Amplitude`。
`ChangeProperty` 那條路怎麼組合都不通。

## 為什麼要做這件事

DDR 接收端的判準位不是固定的一條線。工具原本只在求解器自己算出來的那一個
交越振幅上量眼圖，**回報的數字對 DDR 來說是不完整的**：Vref 偏一點眼寬就變一個樣，
而規格看的是整個 Vref 容差範圍內最差的那一個。

實測這條通道，用反推出來的正確 VDDQ 掃規格 ±6%：

| | Vref (V) | 眼寬 (UI) |
|---|---|---|
| 原本報的（自動判準位） | 0.7577 | 0.9087 |
| 掃描找到的最差 | 0.6668 | **0.8006** |

**原本的數字樂觀了 12%**，也就是 0.108 UI 的餘裕是不存在的。

## 名稱：檔案裡寫的和介面上叫的不一樣

`.aedt` 是文字檔，可以直接翻。判準位在裡面長這樣：

```
$begin 'TraceDef'
  Name='AEYEPROBE(Eye_LANE_1)'
  $begin 'ExtendedTraceInfo'
    AutoCompCrossAmplitude=true
    CrossingAmplitude='0mV'
    AutoCompEyeMeasurementPoint=true
    EyeMeasurementPoint='0ps'
```

看到這個很容易直接拿 `AutoCompCrossAmplitude` 去呼叫 API。**那會失敗。**
屬性格上的名稱是：

| `.aedt` 檔案裡 | 屬性格上（API 要用這個） |
|---|---|
| `AutoCompCrossAmplitude` | `Auto Compute Cross Amplitude` |
| `CrossingAmplitude` | `Crossing Amplitude` |

第一個差了兩個字（多 `Compute`、少 `ing`），第二個剛好只差空格。這種
「一半對得上」最容易讓人以為自己拼對了。

## 四個卡住的地方，依踩到的順序

### 1. `ChangeProperty` 走不通

試過 6 個 tab 名稱（`Eye`／`Trace`／`Attributes`／`Scaling`／`EyeMeasurements`／
`General`）乘以 5 種 PropServer 寫法（`報表:trace`、`trace`、`報表`、
`報表:trace:Curve1`、`Results:報表:trace`），共 30 組，**全部回同一個
`GrpcApiError: Failed to execute gRPC AEDT command: ChangeProperty`**。

而 gRPC 分不出「方法不存在」與「參數錯誤」（見
[量測介面調查](量測介面調查_20260814.md) 第 1 節），所以那 30 個錯誤訊息
一個字都沒告訴我哪裡錯。

### 2. 屬性在自動計算開著的時候是隱藏的

子物件 API 走得通：

```python
report = circuit.odesign.GetChildObject("Results").GetChildObject(plot_name)
trace = report.GetChildObject("AEYEPROBE(Eye_LANE_1)")
trace.GetPropNames()      # 16 項，沒有 Crossing Amplitude
```

`Crossing Amplitude` 不在那 16 項裡。要先關掉自動計算：

```python
trace.SetPropValue("Auto Compute Cross Amplitude", False)
```

### 3. 子物件會快取屬性清單（這一條最貴）

關掉自動之後**沿用同一個 handle 再問，還是 16 項**。

```python
trace.SetPropValue("Auto Compute Cross Amplitude", False)
trace.GetPropNames()                      # 還是 16 項 ← 快取
report.GetChildObject(TRACE).GetPropNames()   # 17 項，多出 Crossing Amplitude
```

**這個症狀跟「這版 AEDT 沒有這個屬性」一模一樣**，沒有任何錯誤訊息。
前後花了四輪探測才問出來——第二輪其實已經寫了「關掉後重新列一次」，
但那一輪重用了同一個 handle，於是得到「關掉也沒有新屬性」這個錯誤結論。

所以程式裡每次都重新取：

```python
def trace():
    return report.GetChildObject(trace_name)   # 屬性清單有快取，一定要重取
```

### 4. 關掉自動而不給值，量測全變 NaN

關掉自動之後 `CrossingAmplitude` 留在預設的 `0mV`。這個眼的準位是
0.4 V 與 1.1154 V，**0 mV 落在眼的外面**，量不到交點，所有量測回 NaN。

那不是壞掉，是機制通了的證據。但如果剛好在這個狀態下讀數，會得到一份
「看起來像失敗」的結果而不知道原因。

## trace 要用「誰有這個屬性」來認，不要用名字

報表底下有六個子物件：

```
AEYEPROBE(Eye_LANE_1)   ← 這個才是 trace
Legend
EyeDiagramPMFComposite
Header
General
EyeDisplayTypeProperty
```

trace 的名字是 `AEYEPROBE(<探棒名>)`，而探棒名由呼叫端決定。拿名字比對等於
把命名慣例寫死，所以程式改成**逐一問誰有 `Auto Compute Cross Amplitude`**。

## 判準位只影響寬度，不影響準位

掃 13 點的實測（自動判準位下準位 0.4000／1.1154 V）：

| Vref (V) | 眼寬 (UI) | 最小眼寬 (UI) | 眼高 (V) | 最小眼高 (V) |
|---|---|---|---|---|
| 0.5431 | 0.6533 | 0.8244 | 0.5778 | 0.6184 |
| 0.6146 | 0.7456 | 0.8842 | 0.5767 | 0.6117 |
| 0.6862 | 0.8239 | 0.9182 | 0.5758 | 0.6100 |
| 0.7577 | 0.9034 | 0.9461 | 0.5752 | 0.6083 |
| **0.8292** | **0.9692** | **0.9721** | 0.5750 | 0.6083 |
| 0.9008 | 0.9065 | 0.9501 | 0.5758 | 0.6100 |
| 0.9723 | 0.7891 | 0.8922 | 0.5776 | 0.6168 |

眼寬與最小眼寬跟著判準位大幅變動（0.65 → 0.97 UI），眼高幾乎不動
（0.5750 ～ 0.5778 V，變化 0.5%）。這與 Ansys 說明文件一致：交越振幅設定的是
「在哪一個電壓上算眼寬」；**眼睛量測點**（時間那一邊）才影響最小眼高，
Vref 掃描掃的是振幅不是時間。

**峰值在 0.8292 V，不在準位中點 0.7577 V。** 眼是不對稱的，
所以任何以中點為中心的掃描窗，最差都會落在低壓那一端。

## 掃描窗放錯地方會給出一個看起來完全正常的錯數字

這是做這件事的過程中自己踩到的，值得寫下來。

規格的 Vref 中心是 0.5×VDDQ。我一開始拿 DDR4 的 1.2 V 去算，窗落在
0.528 ～ 0.672 V。但**這條通道的準位中點是 0.7577 V，反推 VDDQ 約 1.515 V**
（DDR3 的位階），窗整條偏到眼的下緣。

四種窗跑在同一份求解結果上：

| 窗 | 範圍 (V) | 最差眼寬 (UI) | 落在端點 |
|---|---|---|---|
| A. VDDQ 填 1.2 V（錯的） | 0.528 ～ 0.672 | 0.6515 | 否 |
| B. VDDQ 填 1.5155 V（對的） | 0.667 ～ 0.849 | **0.8006** | 是 |
| C. 用量到的準位定中心 ±6% 眼幅 | 0.715 ～ 0.801 | 0.8577 | 是 |
| D. 同上但 ±30% | 0.543 ～ 0.972 | 0.6533 | 是 |

A 的「最差 0.6515」量到的是**「離眼中心很遠」**，不是「Vref 容差內最差」。
兩者的數字長得一模一樣，畫面上沒有任何東西能區分。

所以加了 `check_window_against_levels()`：窗的中心離量到的眼中點超過眼幅的
15% 就出警告，並**把反推出來的 VDDQ 算給使用者**。A 那組會被擋下並顯示
「由量到的準位反推大約是 1.515 V」。

## 最差落在端點就不是最差

上表 B、C、D 三組的 `edge_limited` 都是 `True`——最差點就在掃描範圍的頭。
那代表**真正的最差可能在範圍之外**，這時候該做的是把範圍拉寬再掃一次，
不是拿這個數字去判規格。這也是 `summarize()` 一定要回報這個欄位的原因。
